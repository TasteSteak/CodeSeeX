上游模型选择 — 方案模板

背景：原来的「真实上游模型」三选一（Default / Flash / Pro）已删除，现在模型列表的点击只切换右侧计费卡片。 目标是让「哪个模型真正服务请求」重新可选，且尽量复用已有的模型列表与计费卡片，不新增第三个控件。 以下四份是静态示意，不含后端。

约定

四份方案都遵守同一套语义，区别只在交互落点。

状态含义写入的配置
跟随客户端上游用 Codex 请求里指定的模型（现在的默认行为）override = "default"
锁定模型无论客户端要什么，都用选中的这个模型override = "<slug>"

方案 A 列表即选择器

列表第一行是「跟随客户端」，点其他行直接把该模型设为上游。选中行带「上游」小标签，右侧计费卡片同步显示它的价格。

代理 → 模型行为
当前上游：跟随客户端
跟随客户端 计费按实际使用的模型计算
优点零新增控件，列表已经有点击和选中态；点击行为从「看价格」变成「看价格并用于上游」，心智只有一个。
代价要看另一个模型的价格就会顺手把它设成上游，需要「跟随客户端」那一行足够显眼。

方案 B 行内按钮

点击行仍然是「查看价格」，每行右侧多一个「用于上游」按钮。顶部一条状态说明当前上游是谁。

代理 → 模型行为
当前上游：跟随客户端
跟随客户端 当前查看的模型
优点「浏览价格」和「用于上游」两个动作彻底分开，不会误操作。
代价每行多一个按钮，列表更拥挤；默认那行是唯一没有价格的行，样式要单独处理。

方案 C 卡片头部锁定

列表保持现在的含义（只切换查看的价格）。右侧计费卡片头部加一个开关：把正在查看的模型锁为上游。

代理 → 模型行为
当前上游：跟随客户端
DeepSeek V4 Pro 每 100 万 Token
优点新增面积最小：一个开关。浏览价格的路径完全不变，误操作成本最低。
代价两步操作（先选模型，再锁定）；列表上看不出哪个是上游，得看顶部状态行。

方案 D 独立下拉

模型列表完全不动，在它上面加一行「上游模型」下拉，选项由 catalog 生成，外加一个「跟随客户端」。

代理 → 模型行为
真实发往上游的模型。跟随客户端时使用请求里指定的模型。
DeepSeek V4 Pro 每 100 万 Token
优点最接近被删掉的那个控件，语义直白；下拉由 catalog 生成，不再是写死的 Flash / Pro。
代价多了一个控件，且和下方列表可能显示不一致（下拉选了 Pro、列表在看 Flash）。

我的倾向

A 最省，但它把「看价格」和「改上游」绑在一起；D 最直白，代价是多一个控件。 如果只选一个，我建议 A 的列表加上 C 的卡片开关：列表点击负责选择，卡片上的开关决定这一选择是否真的作用于上游， 同时保留顶部状态行。这样既复用了现有组件，也不会因为想看一眼价格就把上游改掉。等你定方向后我再落实现。
